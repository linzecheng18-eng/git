# AI 图片审美评测助手部署设计

## 1. 产品目标

面向普通图片创作者提供低门槛的图片审美诊断。用户无需注册，选择图片类型并上传单张图片后，系统返回通俗的问题说明和能够直接执行的修改建议。

首版优先验证评测是否准确、建议是否有用，不以建设多个客户端或完整用户系统为目标。

## 2. 用户与支持范围

首批目标用户为普通图片创作者。首版支持以下三类图片：

- 摄影照片
- AI 生成图片
- 社交媒体配图

用户上传前主动选择图片类型。系统采用统一的五维基础评价，并根据图片类型追加专项检查，避免使用一套泛化标准处理所有图片。

## 3. 落地方式

首版采用移动端优先的响应式 Web 应用，同时支持手机和电脑浏览器。

选择 Web 的原因：

- 能直接复用现有本地网页原型，开发和迭代成本最低。
- 一套代码覆盖手机与电脑，无需同步维护多个客户端。
- 不受小程序审核、包体积和平台接口限制。
- 便于公开测试、分享链接和收集匿名评测反馈。

微信小程序不纳入首版。只有在 Web 版本证明需求成立，且主要流量明确来自微信后，才评估小程序。浏览器插件或桌面工作台仅在出现专业用户高频使用需求后考虑。

## 4. 首版功能边界

首版包含：

- 三种图片类型选择
- 单张图片上传与预览
- 图片格式和体积校验
- AI 审美分析
- 一句话总体判断
- 一至三个主要问题
- 每个问题对应的具体修改建议
- 构图、色彩、主体、清晰度、视觉层次五维评分
- 重新评测另一张图片

首版不包含：

- 账号与登录
- 个人历史记录
- 排行榜与社区
- 付费系统
- 批量评测
- 自动修改图片
- 自动生成优化提示词
- 网页与小程序同步开发

## 5. 系统架构

系统由四个边界清晰的部分组成：

1. 响应式网页：负责图片类型选择、上传、预览、进度和结果展示。
2. 后端评测 API：负责文件校验、图片压缩、调用控制、错误处理和隐私清理。
3. 视觉模型适配层：根据图片类型选择提示词并调用视觉大模型。
4. 结果标准化层：校验模型返回结构，统一输出五维评分、问题、建议和总结。

数据流如下：

```text
用户选择类型并上传图片
  -> 前端校验并提交
  -> 后端压缩和标准化图片
  -> 视觉模型按图片类型评测
  -> 后端校验并标准化结果
  -> 前端优先展示问题和建议
```

现有 Python 本地服务继续用于本地验证。公开部署不得直接暴露基于 `http.server` 的开发服务，应替换为生产级 Web 服务。模型 API 密钥只保存在后端环境变量中，不进入前端代码、仓库、日志或示例配置。

## 6. 用户流程

1. 首页明确说明“上传一张图片，获得具体修改建议”。
2. 用户选择摄影照片、AI 生成图或社交媒体配图。
3. 用户上传或拖入单张图片，页面显示预览。
4. 用户点击开始评测，页面展示分析进度。
5. 结果页依次展示总体判断、主要问题、对应建议和五维评分。
6. 用户可点击“重新评测另一张”回到上传状态。

结果页以问题诊断和修改建议为核心。分数只作为辅助信息，不设置排行榜或比较机制。

## 7. 隐私与安全

- 默认不长期保存用户原图。
- 原图仅用于本次评测，处理完成后从临时存储中删除。
- 匿名保留的评测指标不得包含可还原原图或识别用户的信息。
- 限制允许的文件格式、文件体积和请求频率。
- API 密钥不得发送到浏览器，不得写入仓库、日志、测试快照或文档。
- 服务端不得记录图片内容、认证头或包含敏感参数的完整请求体。

## 8. 异常处理

- 不支持的格式或超出体积限制：提交前提示具体限制。
- 图片损坏或无法解析：拒绝评测并提示重新选择图片。
- 模型超时：保留当前页面预览，允许用户重试。
- 模型返回结构异常：后端自动重试一次；再次失败则返回通俗错误提示。
- 服务繁忙、额度不足或上游不可用：明确说明暂时无法评测，不生成模拟结果。

公开环境中的错误响应不得暴露密钥、内部路径、模型原始响应或堆栈信息。

## 9. 测试与验收

功能验收：

- 手机和电脑均能完成选择类型、上传、分析和查看结果的闭环。
- 支持 JPG、PNG 和 WebP，且执行明确的文件体积限制。
- 三种图片类型分别使用专项评测提示词。
- 每次成功结果均包含总体判断、具体问题、对应建议和完整五维评分。
- 超时、无效响应、额度不足和无效图片均有可理解的错误提示。
- API 密钥不出现在前端文件、仓库或日志中。
- 原图在分析结束后删除，不建立用户图片库。

效果验证：

- 使用不少于 50 张真实图片，覆盖三种图片类型。
- 由人工分别判断问题诊断准确性和建议可执行性。
- 问题诊断被认为“基本准确或更好”的比例达到 70%。
- 修改建议被认为“能够直接执行”的比例达到 70%。
- 至少完成一轮基于失败案例的提示词调整，并保留调整前后的结果对比。

## 10. 部署阶段

### 阶段一：本地验证

使用现有本地 Web 原型跑通三类图片的评测流程，完善结果结构、错误处理和测试集。

### 阶段二：公开 Web 测试版

部署响应式前端和生产级后端 API，配置 HTTPS、环境变量、请求限制、临时文件清理和基础监控。发布前完成安全检查与 50 张图片效果验证。

### 阶段三：渠道扩展评估

根据真实用户来源和使用频率决定是否增加微信小程序、浏览器插件或专业工作台，不提前建设这些入口。

## 11. 决策总结

首版以响应式 Web 应用落地，服务普通图片创作者，支持摄影、AI 生成图和社交媒体配图。用户无需注册，上传即用。产品重点是准确指出问题并给出可执行建议，而不是提供排行榜、社区或复杂创作工具。先验证评测质量和真实需求，再决定是否扩展到小程序或专业客户端。
